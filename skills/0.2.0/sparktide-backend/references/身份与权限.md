# 身份与权限

可信身份来自业务系统已经完成的登录。启澜把这份登录转成平台上的用户和租户，并在工具、知识回调时重新进入原认证链。模型输出、请求正文里的用户编号、普通 `context` 和浏览器里的应用标识都不能提升权限。

## 两条凭据

| 凭据 | 放在哪里 | 用途 |
| --- | --- | --- |
| `sparktide.platform.credential` | 只在业务后台 | 注册、核验、发布和能力续租 |
| 用户现有的 Cookie、Bearer 或自定义认证头 | 浏览器发给业务后台的 `/api/ai` | 确定是哪一个业务用户 |

前端 `createClient` 只配置第二种。`identityKey` 是本机用来隔离缓存的非秘密字符串，由主体、租户和登录代次组成；注销返回 `null`。它不发送到服务端，也不充当认证。token 刷新而主体未变时保持原值。未提供 `identityKey` 时，在现有注销或切换用户的代码里调用 `ai.reset()`。`reset()` 清空本地任务和消息，不取消已经提交的后台运行。

## 默认主体映射

Starter 在缺少自定义 Bean 时注册 `BusinessPrincipalMapper`：

- 主体是 `String`：用户标识取该字符串，租户为空。
- 主体是 `Principal`：用户标识取 `getName()`，租户为空。
- 其他类型：返回 `null`，请求变成 401，不会访问平台。

Spring Security 的 `Authentication` 会先取出 `getPrincipal()`。匿名令牌和未认证令牌在此之前拒绝。Shiro 使用当前线程里已经认证的 `Subject`，不重新校验 token，也不新建 `Subject`。

这个默认映射适合主体名就是业务用户编号的系统。自定义用户对象、多租户或不能依赖 `getName()` 时，提供自己的 `BusinessPrincipalMapper`。映射只读已认证对象上的真实字段，使用 `UserIdentity.of(用户标识)` 或 `UserIdentity.of(用户标识, 租户标识)`。用户标识非空且不超过 128，租户可以为空串。不要调用主体的 `toString()`。

::: code-group

```java [Java]
@Bean
BusinessPrincipalMapper businessPrincipalMapper() {
    return principal -> {
        if (principal instanceof BusinessUser user) {
            return UserIdentity.of(user.getUserId(), user.getTenantId());
        }
        return null;
    };
}
```

```kotlin [Kotlin]
@Bean
fun businessPrincipalMapper(): BusinessPrincipalMapper = BusinessPrincipalMapper { principal ->
    if (principal is BusinessUser) UserIdentity.of(principal.userId, principal.tenantId) else null
}
```

:::

`IdentityResolver` 是更底层的接口，入参是容器或 Spring Security 已经认证的 `Principal`。默认配置会先解包，再调用上面的 Mapper。只有登录框架直接给出 `Principal`、且默认解包不适用时，才替换 `IdentityResolver`。两种 Bean 都不做登录校验。

功能权限的默认适配器会在回调时核对同一主体，并调用原框架：

| 已有框架 | 核对方式 |
| --- | --- |
| Shiro | 当前已认证 Subject 的 `isPermitted(权限名)` |
| Spring Security | `GrantedAuthority` 的字符串是否包含声明的权限名 |
| 只有 Servlet 角色 | `HttpServletRequest.isUserInRole` |

数据范围仍由业务 Service 判断。`@Tool(permissions = {"equipment:read"})` 和 `@Agent(permissions = ...)` 使用业务里原有的权限名。平台只传递这些声明。

只依赖当前身份、资源和参数的历史读取，默认适配器实现了合并接口，同一次历史读取里的相同决定可以合并。按单次运行临时决定的自定义 `PermissionProvider` 不参与这种合并。两种实现都不跨请求缓存授权。一个应用最多一个 `PermissionProvider` Bean。

## 回调里的原认证

用户请求进入 `/api/ai` 后，SDK 从白名单头收集已有认证材料，加密成短期胶囊交给平台。工具或知识回调回到本进程时，再经过原来的认证链。默认白名单是 `Authorization`、`Cookie`、`token`、`X-Auth-Token`、`X-Access-Token`、`X-CSRF-Token`、`X-XSRF-Token`。设置 `sparktide.authentication.headers` 会整体替换默认白名单。需要增加业务自定义头时，应同时列出仍需转发的 `Authorization`、`Cookie` 等默认头；未列出的头不会转发。列表最多 32 个，且不能使用 `X-SparkTide-*` 或 `Host`、`Content-Type` 一类协议头。胶囊寿命 `sparktide.authentication.ttl-seconds` 默认 600，范围 1 到 3600。原 token 更早过期或被撤销时，以业务系统为准。

在工具里调用已有远程 API 时，从回调上下文读取凭据，交给原来的客户端：

::: code-group

```java [Java]
BusinessAuthentication auth = context.authentication();
String bearer = auth.token();          // Authorization 为 Bearer 时返回令牌，否则为 null
String shiroToken = auth.header("token");
equipmentClient.call(bearer, input.equipmentId());
```

```kotlin [Kotlin]
val auth = context.authentication()
val bearer = auth.token()
val shiroToken = auth.header("token")
equipmentClient.call(bearer, input.equipmentId)
```

:::

`authentication()` 只在这次回调执行期间可用。到期、回调结束或桥关闭后读取会失败。返回值是秘密：可以传给原业务客户端，不能写入工具结果、日志、模型消息或 `context`。本机 Service 如果已经绑定了原框架的线程上下文，直接调用即可，不必再取出 token。

`ToolContext` 还提供 `userId()`、`tenantId()`、`appId()`、`callId()`、`runId()` 和 `deadline()`。`KnowledgeContext` 同样提供用户、租户和 `authentication()`。`trustedContext()` 是业务边界放入的普通数据，里面不允许覆盖 `appId`、`subjectId`、`tenantId`、`role`、`permissions`。

## 浏览器入口保护

聊天安全过滤只包住 `sparktide.http.path` 及其子路径，默认 `/api/ai`。原业务认证过滤器仍然先执行。SDK 标记自己接管的 JSON 和 SSE，宿主若有通用正文过滤器，可用 `SdkHttpRequest.isManaged(request)` 跳过这些请求。这个标记不授予权限。

| 规则 | 行为 |
| --- | --- |
| Origin | 默认同源。额外来源必须是完整的 `http` 或 `https` origin |
| 查询串里的 token、Authorization、白名单头名 | 401 `UNAUTHENTICATED` |
| 跨源且未列入允许列表 | 403 `ORIGIN_REJECTED` |
| 预检 `OPTIONS` | 204，允许的方法为 GET、POST、PATCH、DELETE、OPTIONS |
| 未进入已认证的 MVC | 按状态返回固定错误码，不把异常正文回给浏览器 |

自动配置在没有自定义 `ChatRequestVerifier` 时使用 `ChatRequestVerifier.existingAuthentication()`。类注释仍写 `bearerOnly`，以这段实现为准。Cookie 写请求的规则是：

- 请求上已有 Spring Security 的 `CsrfToken` 时，对应头必须与 token 一致，否则 403 `CSRF_REQUIRED`。
- 没有该设施时，必须同时具备同源 `Origin` 和 `X-Requested-With: XMLHttpRequest`，否则同样是 `CSRF_REQUIRED`。
- `GET`、`HEAD`、`OPTIONS`，以及没有 `Cookie` 头的请求，不在这里拒绝。

`bearerOnly()` 是可选工厂：非安全方法只要带 `Cookie` 头就返回 403 `CSRF_REQUIRED`。需要这种更严的策略时再自行注册该 Bean。前端 Bearer 和自定义头默认 `credentials: omit`，通常不会带上 Cookie。

前端认证与后台头的对应关系：

| `auth.type` | 浏览器行为 |
| --- | --- |
| 省略或 `cookie` | `credentials` 默认 `same-origin`，带 `X-Requested-With`。CSRF 头默认 `X-CSRF-TOKEN`，可用 `csrfHeader` 和 `csrfToken()` 改 |
| `bearer` | `Authorization: Bearer`，`credentials: omit`。token 空或含换行会在本地拒绝 |
| `headers` | 原样附加业务头，默认 `credentials: omit`。显式改为携带 Cookie 时会加上 `X-Requested-With` |

SDK 拒绝覆盖协议头、`X-SparkTide-Business-*`、重复大小写的头，以及含换行的头值。每次请求和 SSE 重连都重新读取 token，不在 SDK 里缓存。

## 前端上下文和跟进

`context` 在发送前复制为 JSON 快照：普通对象、深度不超过 32、编码后不超过 64KiB。函数形式的 `context` 在每次发送时调用。快照里放项目编号这类业务数据。

跟进命令使用同一条业务认证。`QUEUE` 排到后续运行，`STEER` 指向当前运行的下一个安全点，并且不能改智能体或组件清单。提交成功表示已受理。是否生效看回执状态 `ACCEPTED`、`APPLIED`、`REJECTED`、`CANCELLED`。结果未知时保留原来的幂等键再显式恢复，SDK 不自动重发写请求。`STOP` 是一次原子控制。暂停后的 `RESUME` 复用当前登录，由平台复核是不是同一主体。

页面卸载只停止本地订阅。取消后台任务使用界面上的停止，或对任务句柄调用 `cancel()`。
