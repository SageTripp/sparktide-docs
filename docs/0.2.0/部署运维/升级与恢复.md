# 升级与恢复

升级先备份，再在明确的目标库上执行初始化。初始化只提升平台表，启动过程不会补做这件事。当前执行库格式是 21，不是旧说明中的 18 或 19。


本文不授权在当前仓库机器上初始化、恢复或切换服务。

## 范围

备份工具由部署方提供并自行验证。平台不附带自动备份任务。监控见 [监控与排障](./监控与排障.md)。

## 步骤

1. 确认目标主机、库名和维护窗口。通知调用方停止新的写入，或接受维护期间新请求失败。
2. 对 PostgreSQL 做全库备份，覆盖业务表、原生日志、公共事件、调用和审批事实、人工证据、预算以及凭据密文。metadata 归档快照不是这份备份。
3. 单独备份 `SPARKTIDE_CREDENTIAL_KEYRING`。只恢复数据库而没有同一套密钥时，托管凭据无法解密。
4. 停掉唯一的启澜进程，确认顾问锁已经释放，再启动新版本的初始化。不要在旧进程仍持锁时并行初始化。

独立进程：

```powershell
$env:SPARKTIDE_NODE_DATABASE_URL = Read-Host '目标库连接串'
$env:SPARKTIDE_ALLOW_DATABASE_INITIALIZATION = 'true'
mise exec -- npm run db:initialize
Remove-Item Env:SPARKTIDE_ALLOW_DATABASE_INITIALIZATION
```

容器：

```powershell
$env:SPARKTIDE_DB_PASSWORD = Read-Host 'SPARKTIDE_DB_PASSWORD'
$env:SPARKTIDE_ADMIN_TOKEN = Read-Host 'SPARKTIDE_ADMIN_TOKEN'
docker compose --profile setup run --rm initialize
```

5. 去掉初始化开关后启动一个新进程。就绪检查通过后，再让调用方恢复流量。
6. 抽查一条旧会话、一条模型账本和一条终态运行。未知 `COMMIT`、未知工具副作用和 `UNKNOWN` 预算占用应仍保持未知，而不是变成成功或 0。

从格式 20 及更早版本升级时，初始化把 `st_node_execution_meta.version` 更新为 21，并尽量把会话定义中仍保存的公开消息窗口抄入 `st_node_conversation_message`。它不重建已经不在该窗口里的历史正文。

## 配置

| 对象 | 升级后应看到的值 |
| --- | --- |
| `st_node_execution_meta.version` | `21` |
| `st_node_journal_meta.version` | `1` |
| `st_node_control_meta.version` | `1` |
| `st_node_registry_meta.version` | `1` |
| 成果与预览信用 | `st_node_report_artifact`、`st_node_preview_hold` 仍在。`HELD` 与 `UNKNOWN` 不能清零 |
| 应用回退 | 新程序必须能读 21。不能删新表、把版本号改小，或把未知事实改成成功后再启动旧程序 |

没有旧版程序能够正确识别信用占用的证据时，不要把版本改回 19 或 18。若必须回到升级前状态，在隔离环境恢复升级前备份，并明确升级之后新增事实的损失范围。

留存策略里的清理开关不能当作升级回滚。可靠运行、会话、事件、审批和调用历史不通过普通留存入口删除。

## 结果

- 初始化成功只表示平台表已安装或已升到当前格式。它不重新派发失败任务，也不转换外部数据库。
- 启动时会把本库遗留的活动运行收成失败并推进围栏。审批不会自动通过。
- `DISPATCH_INTENT` 且运行已终态的工具行变成 `UNKNOWN` / `PROCESS_RESTARTED`。
- 恢复演练应先在隔离库完成，再决定是否切换连接串。切换本身要单独确认目标，不能由文档更新触发。
- 人工模型对账只追加证据。合成探测预算修正是另一条显式入口，二者不能互代。
