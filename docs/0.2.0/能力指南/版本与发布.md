# 版本与发布

当前产品版本是 `0.2.0`。执行库当前格式是 **21**。资源发布使用各自的 `x.y.z`，与产品版本不是同一个号码。


## 范围

本文核对版本常量、存储格式和发布动作。升级命令见 [升级与恢复](../部署运维/升级与恢复.md)。兼容矩阵见 [版本与兼容性](../参考资料/版本与兼容性.md)。

## 步骤

1. 用根 `package.json` 的 `version` 确认产品版本，不要用旧架构说明里的格式号代替它。
2. 构建并在目标库上显式执行初始化。该命令把执行库 1 到 20 升级到 21，同时保证日志、控制面和注册表元数据为 1。
3. 启动服务。执行器只接受 `st_node_execution_meta.version = 21`。版本不符时进程在监听前失败。
4. 在控制台发布资源草稿。发布确认后，该 `id@version` 的定义不能再改，只能再发新版本。
5. 切换应用默认 Agent 时带上应用 `revision`。不匹配会得到 412，本地选择不会覆盖服务器。
6. 线协议或 SDK 一起升级时，先保留旧资源版本和已写入消息，再切新绑定。不要用删表或手改版本号回滚。

## 配置

| 常量或对象 | 当前值 | 核对位置 |
| --- | --- | --- |
| 产品版本 | `0.2.0` | 根 `package.json`、镜像 label |
| Node / npm | `24.22.1` / `10.9.4` | `package.json` `engines`，镜像内会检查 npm 版本 |
| DSH 与压缩、会话包 | `0.2.1-rc.3` | 根依赖，且为唯一 Agent 循环 |
| 执行库 | `EXECUTION_STORE_VERSION = 21` | `st_node_execution_meta` |
| 日志库 / 控制库 / 注册表 | 均为 `1` | `st_node_journal_meta`、`st_node_control_meta`、`st_node_registry_meta` |
| 格式 20 保留的成果表 | `st_node_report_artifact` | 升到 21 时不删除 |
| 格式 21 新增的展示历史 | `st_node_conversation_message` | 只迁移定义里仍保存的公开窗口，不猜测已截断正文 |
| 机器合同 | `contracts/` 下五份 JSON | 合同操作不等于服务已开放 |
| 契约清单格式 | 工具脚本 `FORMAT_VERSION = 2` | 只约束契约清单文件，不是执行库格式 |

旧运维说明中的执行库 18 或 19 不能再当作当前启动门槛。格式 19 引入的预览信用表仍然保留；没有旧程序兼容证据时，不能把元数据版本改回 18 或 19 来声称可以安全降级。

初始化可接受现存版本 1 到 21。除此之外的版本会在升级事务中拒绝。本仓库不提供自动降级脚本。

## 结果

- 就绪检查在日志库和控制库都为 1、注册表条件满足、执行器仍持有单活锁时返回 `{ "status": "UP", "implementation": "nodejs" }`。
- 健康不表示业务权限、解析器、字体、OIDC 或厂商都已就绪。
- 资源状态为 `DRAFT`、`PUBLISHED` 或 `REVOKED`。应用状态另有 `ACTIVE`、`SUSPENDED`、`ARCHIVED` 等服务端返回值，控制台原样显示。
- 契约就绪门要求每项为已核实且有证据。清单中的待验收项不会因为测试数量增加而自动改成完成。
